## Product vision and approved boundaries

Mebooru is a personal, local-first image/media viewing and organization application, evolved from Monbooru and Monloader. One repository, one installation, one UI, one settings experience and one application lifecycle. Efficiency matters, but minimizing process count or package size is not a goal in itself.

- Preserve independent galleries, database-first organization, managed/referenced media, original media quality, search, tags/aliases/relationships, duplicates, source provenance, rating controls, video previews and optional local AI. Preserve existing support for user-supplied media formats; do not create compressed archives as part of acquisition.
- Meloader becomes an internal managed acquisition worker, not a separately navigated application. No user-facing companion pairing, second settings page, manual port setup or separate launch is required in the finished product. Keep explicit approval for genuinely external plugins.
- Separate library data ownership from acquisition state ownership. The library owns media and gallery databases; the acquisition worker owns queues, watches, source caches and download bookkeeping. Transfer approved files and metadata through a narrow interface; do not write gallery databases directly from the worker.
- Hybrid lifecycle (Option C): start/wake the worker for acquisition requests and scheduled watches while Mebooru is open; stop when safely idle as appropriate. Explicit offline control blocks network-capable work, preserving local browsing and durable queued state. No requirement to operate after app close; no hidden agents or OS background services by default. A prominent Quit Mebooru action stops owned services gracefully.
- Preserve the offline library / WAN-capable acquisition boundary, strict metadata-first blacklist checks (fail closed), source rating and taxonomy evidence, verified alias matching, provenance and manual user overrides. Separate processes are not an OS-enforced sandbox; evaluate least-privilege controls during worker design. No bypass of source restrictions or rate limits.
- Bundle a self-contained gallery-dl runtime with verified managed updates and rollback; no ordinary user requirement for Homebrew or Python. Version 1.32.19 is the current strict transfer code's exact accepted version; validate any change before activation.
- Personal-use project: no separate licensing-analysis workstream. Retain existing license/attribution files and history during import. Distribution, signing and platform packaging remain separate future decisions.

### II.6.1 — Private worker protocol v1 (approved direction; implementation staged)

The internal protocol is separate from the external HTTP API version. Implement in a new `shared/workerproto` package; no production caller or listener changes in this substep. The current library loopback web UI remains unchanged; legacy first-party HTTP is temporary compatibility only. Existing persistent IDs, paths, source metadata and external plugin permissions are not renamed or widened.

**Trust and direction.** The supervisor launches the known bundled sibling with inherited duplex channels (not arbitrary discovered endpoints); each launch is a new connection/session. Validate protocol version and roles before accepting operations; v1 requires exact agreement initially, no silent downgrade to HTTP. The connection identifies the intended peer, not an OS-enforced trust boundary against other same-user code. No bearer secrets on argv, environment, JSON logs, or browser. External plugins cannot call the private dispatcher. Explicit direction and capability checks at dispatch; no generic HTTP proxy, URL fetch, SQL, arbitrary file path, command execution, delete-gallery/media or credential-export method. Existing library authorization and gallery validation remain authoritative. A worker's self-reported approval alone cannot substitute for the existing fail-closed transfer checks.

**Message model.** Request, response, cancel and event have distinct kinds; each request ID is nonzero and unique for the life of the initiating endpoint in that session. Responses and cancel refer to that endpoint's request; IDs are not durable job/import identifiers. Exactly one terminal response per accepted request unless connection loss; success and error are exclusive. Unknown operations, wrong direction and malformed payloads refuse; unknown major protocol version fails closed. Request correlation, cancellation, bounded concurrent requests, bounded event queue and an independent reader/writer are required to prevent deadlock when worker calls the library during a library request. No assumptions of ordered completion. Progress events are hints; queue snapshots and persisted terminal outcomes are authoritative. Sequence/reconnect semantics must not require replay of stale events. Error codes distinguish protocol errors, offline, unauthorized, unsupported, invalid, busy, canceled, interrupted and existing domain outcomes; safe diagnostics, not raw secrets or request bodies. Use existing `shared/contract` DTOs for metadata, lookup, PTR and outcomes where practical; define typed payloads per operation as adapters are built. No untyped method that executes arbitrary user data.

**Framing proposal for II.6.2.** Bounded length-prefixed frames over inherited stdio/handles (stdout reserved exclusively for protocol, stderr for redacted diagnostics). ## Development workflow

**Approved 2026-11-25: milestone-level verification, not one full matrix per small commit.** Work in the consolidated repository on feature branches off `mebooru-foundation`; the original Meloader repository is frozen. Do not push feature work directly to the development branch or upstream-derived `main`. Keep small reviewable commits for implementation, tests, reconciliation and extraction; group related changes into a single milestone PR. Product behavior, trust, privacy and conceptual changes still require explicit discussion. Reliability work within the agreed scope may proceed without intermediate approvals.

- **Development:** create or convert the milestone PR to draft; perform targeted package tests, source review and dependency parity checks as applicable after each coherent change. Use `GOWORK=off go test ./internal/...` only when that is the intended scope, or `make test-all` for all three modules. Draft pushes run fast Linux tests of all modules, not the full matrix; do not wait on slow unrelated hosted jobs to prepare the next commit. - **Milestone gate:** mark the final PR ready for review only when its implementation is complete. Full existing native five-platform matrix, bundled Mac lifecycle/refusal checks, race/vet for all modules, pinned strict transfer, both Docker compile stages and Go/Actions/JS/C++ CodeQL run on ready PRs (including subsequent pushes) and on manual workflow dispatch. No automatic merge; obtain explicit owner acceptance for functional milestones, with a single combined Mac smoke test when needed.
